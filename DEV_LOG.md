### **День 1: Уточнение Архитектуры: PHP-Сайт для Разработки и Шаблоны Структуры Страниц**

**Дата:** 30.08.2025

**Статус:** Фиксация обновленного процесса разработки и уточнение концепции шаблонов страниц.

**Описание:**

Сегодняшнее обсуждение привело к значительному улучшению рабочего процесса и пониманию того, как WebForge будет функционировать на этапе разработки, а также уточнило концепцию шаблонов страниц.

**Ключевые принятые решения:**

1.  **`webforge.json` как Единственный Источник Правды (SSOT):**
    *   Подтверждена и усилена роль `webforge.json` как центрального, декларативного файла, содержащего всю структуру, контент и глобальные настройки сайта. Это обеспечивает единый, версионируемый источник данных для всего проекта.

2.  **Введение Полноценного PHP-Сайта для Разработки (`_dev_site/`):**
    *   **Новый подход:** Вводится промежуточная фаза, где `webforge.json` трансформируется в полноценный PHP-сайт для разработки.
    *   **Скрипт `webforge_php_generator.php`:** Этот скрипт читает `webforge.json` и генерирует динамический PHP-сайт в отдельной директории (`_dev_site/`).
    *   **Содержимое `_dev_site/`:** Включает сгенерированные PHP-файлы для каждой страницы (например, `index.php`, `about.php`), которые используют общие PHP-компоненты (из `components/`) и PHP-макеты (`layouts/`).
    *   **Фаза Разработки:** Разработчик запускает стандартный PHP-сервер, указывая корневой директорией `_dev_site/`. Это позволяет полноценно использовать инструменты PHP-разработки, отладчики и IDE.
    *   **Передача Данных Компонентам:** PHP-файлы компонентов (например, `components/header/header.php`) будут получать данные (как специфичные для экземпляра, так и глобальные) через глобальные переменные (например, `$data` для данных компонента, `$globalConfig` для настроек из `webforge.json.theme` или `webforge.json.navigation`).
    *   **Упрощение `build.php`:** Роль скрипта статической сборки `build.php` теперь сводится к "обходу" сгенерированного PHP-сайта в `_dev_site/`, инклуду PHP-файлов страниц, захвату их вывода и сохранению как статических `.html` файлов.

3.  **Анализ Размера `webforge.json` и Масштабируемость:**
    *   **Вывод:** Проведенный анализ показал, что для предполагаемых масштабов проекта (от 10 до 2500 страниц) размер единого `webforge.json` (ориентировочно 2-10 МБ) не является критической проблемой для производительности PHP-интерпретатора. Единый SSOT остается жизнеспособным и эффективным решением.

4.  **Уточнение Концепции Шаблонов для PageBuilder (Структурные Скелеты Страниц):**
    *   **Разграничение:** Проведено четкое разграничение между "шаблонами контента" (предзаполненные компоненты) и "шаблонами структуры страниц" (скелеты страниц). Фокус сделан на последних.
    *   **Назначение:** Структурные шаблоны определяют базовый макет страницы, расположение компонентов-плейсхолдеров, количество и соотношение колонок, варианты адаптивности, а также могут задавать тип используемого меню или макета страницы (например, "Главная страница: герой + 3 колонки").
    *   **Хранение:** Шаблоны будут храниться в JSON-файле (например, `webforge_page_structure_templates.json`), содержащем `id`, `name`, `description`, `category`, `previewImage`, и ключевое поле `templateStructure`.
    *   **`templateStructure`:** Это поле будет имитировать структуру объекта `page` из `webforge.json` (`layout`, `meta`, `components`), но с минимальными или плейсхолдерными данными для компонентов. При использовании PageBuilder, `instanceId` для компонентов будут генерироваться динамически для обеспечения уникальности.
    *   **Применение:** При создании новой страницы, пользователь выбирает такой структурный шаблон. PageBuilder копирует `templateStructure` в `webforge.json` для новой страницы.
    *   **Перспектива:** Эта концепция является основой для создания будущего `TemplateBuilder` или функции "сохранить как шаблон" в редакторе.

**Следующие шаги:**

1.  Реализация скрипта `webforge_php_generator.php`.
2.  Разработка базовых PHP-компонентов, которые смогут принимать данные.
3.  Начало формирования библиотеки структурных шаблонов страниц.

### **День 0: Инициализация проекта и Фундаментальные Архитектурные Решения**

**Дата:** 27.08.2025 (Дата инициализации, записи могут быть позднее)

**Статус:** Определение и фиксация фундаментальной архитектуры, принципов и ключевых решений.

**Описание:**

Данный пост фиксирует базовые принципы и наиболее важные архитектурные решения, принятые на старте проекта, которые формируют его основу. Эти решения будут служить ориентиром для всей дальнейшей разработки.

**Ключевые принятые решения:**

1.  **Основной стек и Цель Проекта**:

    *   **Генератор**: PHP для разработки и динамической сборки страниц из компонентов на локальном сервере.

    *   **Продакшн**: Полностью статические HTML, CSS, JS файлы, генерируемые скриптом сборки.

    *   **Конечный продукт**: Автономные, высокопроизводительные, SEO-оптимизированные статические сайты, не требующие серверного взаимодействия и внешних зависимостей (включая шрифты), максимально устойчивые к блокировкам.

    *   **Приоритет деплоя**: Максимальная скорость загрузки, отказоустойчивость, независимость, SEO. Читаемость кода не важна.

2.  **Архитектура компонентов**:

    *   **Структура**: Каждый компонент изолирован в своей директории `components/{имя-компонента}/`.

    *   **Состав**: Компонент включает `{имя}.php` (PHP-шаблон для HTML-разметки и минимальной логики), `{имя}.json` (данные/настройки компонента, **не содержит CSS-правил**) и, при необходимости, `script.js` (локальный JS).

3.  **Глобальная конфигурация**:

    *   Файл `site.json` в корне проекта служит единым источником правды для глобальных настроек (цветовая палитра, типографика, брейкпоинты, размеры контейнеров, глобальные данные сайта). Эти данные используются для генерации CSS-переменных и контента.

4.  **Управление уникальностью экземпляров компонентов (HTML ID)**:

    *   **Проблема**: Конфликты HTML `id` при множественном использовании компонента на одной странице.

    *   **Решение**: В PHP-файле каждого компонента генерируется уникальный базовый ID, основанный на имени его директории (`$componentBaseId = basename(__DIR__);`). Все внутренние `id` элемента генерируются с этим префиксом (например, `$componentBaseId . '-header'`), что гарантирует их уникальность. Предполагается, что каждая вставка компонента будет иметь уникальное имя папки (или это будет обеспечено на уровне сборки страницы).

5.  **Изоляция JavaScript**:

    *   **Проблема**: Избежать конфликтов и обеспечить, чтобы JS компонента влиял только на свой экземпляр.

    *   **Решение**: Если у компонента есть `script.js`, его PHP-файл генерирует `inline`-скрипт. Этот скрипт ожидает `DOMContentLoaded`, находит конкретный экземпляр компонента по его уникальному HTML `id` и вызывает общую функцию-инициализатор, **передавая ей найденный HTML-элемент (контейнер компонента)**. Весь JS-код в `script.js` работает **только в контексте переданного элемента** (`element.querySelector(...)`). **Полный отказ от глобальных ID и событий в JS**.

6.  **Архитектура CSS (фундамент)**:

    *   **Модульность**: Каждый компонент будет иметь свой собственный CSS-файл внутри своей директории (`components/{имя-компонента}/style.css`).

    *   **Глобальный CSS**: Основные CSS-файлы (`css/base.css`, `css/layout.css`) будут содержать только глобальные стили (переменные, нормализация, базовые стили тегов) и определения сеток макетов (CSS Grid Layouts).

    *   **Генерация переменных**: PHP-утилита читает `site.json` и генерирует CSS-файл с переменными (`:root`).

    *   **Типографика**: `html { font-size: 100%; }` и `body { font-size: 1.125rem; }` для доступности и желаемого базового размера.

    *   **Нормализация**: Используется Modern Normalize.

**Текущая главная задача и открытые вопросы (на момент "Дня 0" - переходящие на следующие дни):**

*   **Стратегия CSS-нейминга и конфликтов имен**: Как избежать конфликтов CSS-классов в масштабируемом проекте при модульной структуре CSS (например, БЭМ, уникальные префиксы, CSS Modules при сборке) и с учетом методики `scoped-стилизации`.

2.  Приступить к разработке скрипта сборки (`build.php`).

3.  Реализовать механизм генерации CSS-переменных из `site.json`.
