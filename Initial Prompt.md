### Расширенный Промпт для LLM: Проект "WebForge" – Статический Генератор Сайтов для Устойчивой Среды

**Глубинная цель и мотивация проекта (для полного понимания LLM):**

Проект "WebForge" создается в условиях нарастающих информационных ограничений и блокировок, как со стороны государства, так и со стороны международных сервисов. Основная задача — обеспечить функционирование веб-ресурсов для малого бизнеса, которые будут максимально устойчивы к внешним воздействиям, работать на слабом оборудовании и не требовать постоянного обслуживания. Это достигается за счет создания **полностью статических, автономных, независимых от серверного взаимодействия и внешних зависимостей (включая шрифты) сайтов**. При этом ключевым фактором является **высочайшая SEO-оптимизация** для снижения операционных затрат и обеспечения максимальной выгоды в сложных условиях.

**Цель проекта (техническая):**

Создание высокопроизводительного, SEO-оптимизированного статического генератора сайтов, **реализованного на PHP**. Этот генератор будет преобразовывать компонентную структуру проекта в **чистые, автономные, статические HTML, CSS и JS файлы**, не требующие серверного взаимодействия для функционирования. Главный приоритет финальной сборки — **максимальная скорость загрузки, исключительная отказоустойчивость, независимость от внешних ресурсов и превосходные показатели SEO**. Читаемость и поддерживаемость кода деплоя не важны, главное — функциональность в жестких условиях.

**Философия и ключевые принципы:**

*   **Абсолютная автономность**: Сгенерированные сайты не должны иметь зависимостей от внешних CDN, API, шрифтов или любых других ресурсов, которые могут быть заблокированы или недоступны. Все необходимое должно быть включено в статический пакет.

*   **Высочайшая производительность**: Достигается за счет полного отказа от серверной логики на продакшене, минимизации ресурсов, оптимизации изображений, критического CSS. Сайт должен работать максимально быстро даже на слабом оборудовании.

*   **Исключительная отказоустойчивость и взломоустойчивость**: Отсутствие серверной части на продакшене делает сайт иммунным к большинству стандартных атак и проблем с хостингом.

*   **Без сторонних фреймворков**: Весь HTML, CSS, JavaScript пишется с нуля. Идеи визуального вида могут быть заимствованы из существующих библиотек (например, Bootstrap), но **реализация всегда кастомная, путем декомпозиции и переработки идей в полностью изолированные, независимые компоненты собственного изготовления.**

*   **Mobile-First**: Стилевое проектирование начинается для минимального разрешения (320px) и расширяется для больших экранов через медиа-запросы. Использование относительных единиц (`rem`, `em`, `%`, `vw`/`vh`) вместо фиксированных (`px`).

*   **PHP для разработки, Статика для деплоя**: Удобная разработка на локальном PHP-сервере с live-preview. Финальный результат — оптимизированная статическая сборка для публикации.

*   **Минимум JavaScript**: Приоритет отдается решениям на HTML/CSS. JavaScript используется только в случаях, когда CSS не справляется с реализацией эффектов или функциональности. **Предпочтение нативным HTML-элементам**, если они обеспечивают нужную функциональность без JS (например, `<details>` и `<summary>` для аккордеона).

*   **Семантическая верстка**: Финальная сборка должна включать корректное использование тегов `<header>`, `<main>`, `<footer>` и других для улучшения SEO и доступности.

*   **Максимальная SEO-оптимизация**: Облегченный код, быстрая загрузка, семантическая верстка, корректные мета-теги, критический CSS, исключение блокирующих рендеринг ресурсов.

*   **Стратегический поворот в концепции**: Проект изменил позиционирование с "производителя/монтажника" на "инноватор, лидер отрасли с патентами". Это стратегическое изменение, требующее пересмотра структуры и контента, начиная с mobile-first.

**Архитектура проекта (текущая версия, включая принятые решения):**

1.  **`webforge.json`: Единственный Источник Правды (SSOT)**
    *   Центральный, декларативный JSON-файл, содержащий всю структуру сайта, данные страниц, компонентные данные для каждого экземпляра, глобальные конфигурации (например, настройки темы, навигационные структуры).
    *   Все настройки, ранее содержавшиеся в `site.json` (цвета, типографика, брейкпоинты, общая информация о сайте), теперь интегрированы в `webforge.json`.
    *   Масштабируем, даже для крупных сайтов (2-10 МБ).

2.  **Компонентная система:**
    *   Каждый компонент — это отдельная директория в `/components/`.
    *   **`{имя_компонента}.php`**: PHP-шаблон, генерирующий HTML, содержит минимальную PHP-логику для вывода данных и базовых структур (циклы, условия). **Получает данные для своего экземпляра через переменную `$data` и глобальные настройки через `$globalConfig`**.
    *   **`script.js` (опционально)**: Локальный JavaScript для конкретного компонента.

3.  **Структурные Шаблоны Страниц для PageBuilder:**
    *   Это не просто контентные компоненты, а **структурные "скелеты" страниц**, определяющие базовый макет (расположение компонентов-плейсхолдеров, колонки, адаптивность).
    *   Хранятся в отдельном JSON-файле (например, `webforge_page_structure_templates.json`).
    *   Каждый шаблон включает: `id`, `name`, `description`, `category`, `previewImage` (опционально), и `templateStructure`.
    *   `templateStructure` имитирует структуру объекта `page` из `webforge.json` (`layout`, `meta`, `components`), но с минимальными или плейсхолдерными данными для компонентов.
    *   При использовании в PageBuilder, `templateStructure` копируется в `webforge.json` для новой страницы, и все `instanceId` компонентов генерируются уникально.

4.  **CSS-структура (финализированные подходы и текущие вопросы):**
    *   **Генерация CSS-переменных**: Отдельная PHP-утилита читает `webforge.json` и генерирует CSS-файл с переменными (`:root`).
    *   **Базовая типографика и единицы измерения (решено)**: `html { font-size: 100%; }` и `body { font-size: 1.125rem; }`. Все остальные отступы/поля в `rem`, медиа-запросы в `em`.
    *   **Сброс стилей (решено)**: Используется Modern Normalize.
    *   **Макеты (Layouts, решено)**: Предопределенные **CSS Grid Layouts** (использующие `grid-template-areas`) в глобальном CSS. Активируются классами на `<body>`.
    *   **Модульность CSS Компонентов (ключевое решение)**: Каждый компонент имеет свой `style.css` внутри своей директории. Глобальный CSS содержит только общие стили. Scoped-стилизация через классы корневого контейнера компонента.
    *   **Проблема уникальности CSS-селекторов/классов (открытый вопрос, зафиксирована)**: Как избежать конфликтов имен при модульной структуре CSS (например, БЭМ, уникальные префиксы, CSS Modules при сборке).

**Ключевые реализованные решения (подтверждено и детализировано):**

1.  **Уникальные HTML ID для экземпляров компонентов**:
    *   В PHP компонента: `$componentBaseId = basename(__DIR__);`.
    *   Внутренние ID генерируются с суффиксами (например, `$componentBaseId . '-header'`, `$componentBaseId . '-item-' . $index`).
    *   **Важно**: Предполагается, что **каждая вставка компонента будет иметь уникальное имя папки** (или это будет обеспечено на уровне сборки страницы).

2.  **Изолированный JavaScript для компонентов**:
    *   PHP-файл компонента проверяет наличие `script.js` и, если он есть, генерирует `inline`-скрипт.
    *   Этот `inline`-скрипт ждет `DOMContentLoaded`, находит конкретный экземпляр компонента по его уникальному HTML `id`.
    *   `inline`-скрипт вызывает общую функцию-инициализатор (например, `initializeComponent`), **передавая ей найденный HTML-элемент (контейнер компонента)**.
    *   Локальный `script.js` компонента написан так, чтобы принимать этот элемент и работать **только в его контексте**, используя `componentElement.querySelector()` для поиска внутренних элементов.
    *   **Полный отказ от глобальных ID и событий в JS** — всё делается через локальные классы или `data`-атрибуты внутри контекста компонента.

**Процесс разработки и сборки (обновленный):**

1.  **Инициализация проекта**:
    *   Запуск локальных PHP/JS утилит для автоматического создания каталогов компонентов, базовой структуры файлов и настроек.
    *   Формирование глобального `webforge.json` и базового CSS-файла.

2.  **Фаза генерации сайта для разработки**:
    *   **Новый ключевой скрипт**: `webforge_php_generator.php` читает `webforge.json`.
    *   **Цель**: Генерирует полную, динамическую PHP-версию сайта в отдельную директорию (например, `_dev_site/`).
    *   **Содержимое `_dev_site/`**: Включает сгенерированные PHP-файлы для каждой страницы, копии PHP-файлов компонентов из `components/`, PHP-файлы макетов из `layouts/` (если применимо), а также необходимые ассеты.

3.  **Динамичная разработка и отладка (Локальный PHP-сервер)**:
    *   Разработчики запускают стандартный PHP-сервер (Apache, Nginx или встроенный) с корнем в `_dev_site/`.
    *   Это обеспечивает **полную отладку PHP** (Xdebug), знакомый рабочий процесс и динамические предпросмотры страниц.
    *   Компоненты подключаются динамически через PHP, получая данные, сгенерированные из `webforge.json`.
    *   **Приостановка кодирования**: Согласовано, что сначала обсуждается и согласовывается концепция/структура, затем — реализация в коде.

4.  **Статическая сборка**:
    *   После утверждения всех изменений запускается скрипт сборки (`build.php`).
    *   **Обновленная роль `build.php`**: Теперь он "обходит" динамически сгенерированный PHP-сайт в `_dev_site/`, выполняет каждый PHP-файл страницы, захватывает его вывод и сохраняет как статический `.html` файл в директории `build/`.
    *   Также занимается агрегацией, минификацией и копированием CSS и JavaScript файлов в `build/`.
    *   В финальной сборке все CSS-файлы (base.css, layout.css, component.css из папок компонентов) и JS-файлы **объединяются и минимизируются** в один `style.css`/`script.js`.
    *   Код финальной сборки оптимизирован для скорости и SEO (минимизация, объединение, **Critical CSS**, семантическая верстка).

5.  **Автоматизация (локальные утилиты)**:
    *   Интеграция собственных утилит на PHP и JavaScript для:
        *   Генерации CSS из `webforge.json`.
        *   Автоматизации минификации, объединения файлов.
        *   Поддержки live-preview.
        *   Генерации финальных статических файлов.
    *   Важность автоматизации генерации файлов и шаблонов для новых блоков.

**Важные Заметки для LLM:**

*   **Правила синтаксиса Mermaid-диаграмм:**
    *   Текст внутри узлов (круглые `()`, квадратные `[]`, фигурные `{}` или другие скобки), который содержит переводы строк (`<br>` или `\n`), специальные символы или является длинным, **должен быть заключен в двойные кавычки (`"`)**. Пример: `A["Мой <br> длинный <br> текст"]`.
    *   Названия `subgraph` не заключаются в кавычки. Пример: `subgraph Моя Подгруппа`.
    *   Соблюдение этих правил помогает избежать ошибок парсинга, таких как "Parse error on line X: ... Expecting ..., got 'PS'".
